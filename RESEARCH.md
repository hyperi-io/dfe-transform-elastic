# DFE Transform Elastic - Research

## Project Goal

Rust-optimised transform pipeline for Elastic Stack data ingested via Kafka (JSON).
Replaces Vector VRL transforms with native Rust for all Beats sources and Elastic Agent data.

**Input:** JSON events from Kafka (all beats: filebeat, winlogbeat, metricbeat, auditbeat, heartbeat, packetbeat + elastic-agent)
**Transform:** Painless script / ingest pipeline logic -> native Rust
**Output:** Transformed, normalised events

---

## Architecture Overview

```
Kafka (JSON) -> simd-json deserialize -> Rust transforms -> output
                                              |
                              ┌───────────────┼───────────────┐
                              │               │               │
                         field extract   field mutate    enrichment
                         (grok/regex     (rename, set,   (geoip, ua,
                          -> efficient    convert, etc)   community_id)
                          native parse)
```

## 1. elastic_to_rust Transpiler (Reusing elastic_to_vrl)

### What We Have

The existing `/projects/elastic_to_vrl/` project provides:

- **ANTLR4 Painless parser** (Rust, via antlr-rust 0.3.0-beta) - parses Painless scripts into ASTs
- **28 Elastic ingest processor transpilers** - json, csv, grok, dissect, kv, set, append, remove, rename, split, uppercase, lowercase, trim, geoip, user_agent, registered_domain, community_id, network_direction, foreach, pipeline, drop, script, date, convert, fingerprint, uri_parts
- **Pipeline deserializer** - strongly-typed Rust structs for Elastic YAML pipelines
- **Validate + Transpile traits** - clean trait-based architecture
- **Go template code generation** (gtmpl crate) - renders output from processor-specific templates
- **E2E test framework** - integration tests with real log samples per Beats module

### Reuse Strategy: elastic_to_rust

The elastic_to_vrl codebase is structured for reuse. The key change is swapping the **code generation backend** from VRL to Rust:

```
                    elastic_to_vrl                    elastic_to_rust
                    ──────────────                    ───────────────
Input:              Elastic YAML pipeline             Same
Painless parser:    ANTLR4 -> AST                     Same (reuse entirely)
Pipeline parsing:   Processor structs                 Same (reuse entirely)
Validation:         Validate trait                    Same (reuse entirely)
Transpile target:   VRL strings via gtmpl             Rust code via templates
Output:             .yml with VRL source blocks       .rs files with transform fns
```

**What changes:**
1. **Template layer** - swap VRL templates for Rust code templates
2. **Type system mapping** - VRL's dynamic types -> Rust's `serde_json::Value` or typed structs
3. **Runtime library** - VRL built-ins (parse_regex, parse_json, etc.) -> Rust equivalents

**What stays the same (~70-80% of codebase):**
1. All ANTLR4 Painless parsing
2. All pipeline YAML deserialization
3. All processor struct definitions
4. Validation logic
5. Conditional/control flow transpilation structure
6. Test framework structure

### Transpiler Output Design

Each Elastic ingest pipeline becomes a Rust module:

```rust
// Generated by elastic_to_rust from filebeat/module/dns/pipeline.yml
use dfe_transform_elastic::prelude::*;

pub fn transform(event: &mut Event) -> Result<()> {
    // set processor
    event.set("event.kind", "event")?;

    // grok processor -> compiled efficient parser (see section 2)
    if let Some(message) = event.get_str("message") {
        let parsed = parsers::dns::parse_query_log(message)?;
        event.set("dns.question.name", parsed.question_name)?;
        event.set("source.ip", parsed.source_ip)?;
        event.set("source.port", parsed.source_port)?;
    }

    // date processor
    if let Some(ts) = event.get_str("_temp.timestamp") {
        event.set("@timestamp", parse_timestamp(ts, "%Y-%m-%dT%H:%M:%S%.fZ")?)?;
    }

    // geoip processor
    if let Some(ip) = event.get_str("source.ip") {
        enrich_geoip(event, ip, "source.geo")?;
    }

    Ok(())
}
```

### Realism: 95% Auto-Generation Target

**High confidence (near 100% auto-gen):**
- set, append, remove, rename, uppercase, lowercase, trim
- convert (type coercion)
- date (timestamp parsing)
- drop (conditional drop)
- split, join
- uri_parts

**Medium confidence (90%+ auto-gen, may need hand-tuning):**
- grok -> generates calls to efficient parser functions (see section 2)

1. Fork elastic_to_vrl into elastic_to_rust
2. Replace gtmpl VRL templates with Rust code templates
3. Build the `dfe-transform-elastic` runtime crate (Event type, parser library, enrichment)

5. Test against the same E2E test data
6. Hand-tune the remaining ~5%

## 2. Grok/Regex -> Efficient Native Rust Parsing Library

### The Problem

Grok patterns and regexes are the #1 performance bottleneck in log processing pipelines. They are:
- **Backtracking-prone** - a single poorly-written alternation can cause exponential time
- **Opaque** - the regex engine does work the programmer could express more efficiently
- **Untyped** - everything is a string match, requiring post-parse type conversion
- **Redundant** - most grok patterns match highly structured data that doesn't need regex at all

### The Solution: `dfe-parse` Library

A library that provides efficient, hand-optimised Rust equivalents for common grok/regex patterns, plus a macro/codegen system for converting arbitrary patterns.

#### Layer 1: Common Pattern Replacements (Zero Regex)

Replace the most-used grok patterns with purpose-built parsers:

| Grok Pattern | What It Does | Efficient Rust Replacement |
|---|---|---|
| `%{IP}` / `%{IPV4}` | Match IP address | `parse_ipv4(s)` - validate octets directly, ~10x faster |
| `%{IPV6}` | Match IPv6 | `parse_ipv6(s)` - colon-group parser |
| `%{IPORHOST}` | IP or hostname | `parse_ip_or_host(s)` - try IP first, fall back to hostname rules |
| `%{INT}` / `%{NUMBER}` | Integer/number | `parse_int(s)` / `parse_number(s)` - direct digit scan |
| `%{WORD}` | `\w+` | `take_while_alphanumeric(s)` - byte-level scan |
| `%{GREEDYDATA}` | `.*` | Just take the remaining slice (zero cost) |
| `%{TIMESTAMP_ISO8601}` | ISO timestamp | `parse_iso8601(s)` - fixed-position field extraction |
| `%{SYSLOGTIMESTAMP}` | Syslog time format | `parse_syslog_timestamp(s)` - month lookup table + digit parse |
| `%{LOGLEVEL}` | Log level keyword | `parse_loglevel(s)` - aho-corasick or match on first byte |
| `%{QUOTEDSTRING}` | Quoted with escapes | `parse_quoted(s)` - memchr for quote, handle escapes |
| `%{HOSTNAME}` | DNS hostname | `parse_hostname(s)` - label-dot-label validation |
| `%{MAC}` | MAC address | `parse_mac(s)` - fixed 6-group hex parse |
| `%{URI}` / `%{URIPATH}` | URI components | `parse_uri(s)` - scheme://authority/path?query#fragment |
| `%{EMAILADDRESS}` | Email | `parse_email(s)` - local@domain split + validation |
| `%{UUID}` | UUID | `parse_uuid(s)` - fixed 8-4-4-4-12 hex pattern |

These parsers use:
- **memchr** for SIMD-accelerated delimiter finding
- **Direct byte inspection** (`s.as_bytes()[i]`) instead of character iteration
- **Lookup tables** for character class membership (is_digit, is_hex, etc.)
- **No allocation** - return `&str` slices into the original input

#### Layer 2: Composite Pattern Parser Generator

For full grok patterns like:
```
%{IPORHOST:source.ip}:%{INT:source.port:int} -> %{IPORHOST:dest.ip}:%{INT:dest.port:int}
```

Generate a Rust function at **build time** (proc macro or build.rs codegen):

```rust
// Auto-generated from grok pattern
pub fn parse_connection(input: &str) -> Result<ConnectionFields<'_>> {
    let (input, source_ip) = parse_ip_or_host(input)?;
    let input = expect_byte(input, b':')?;
    let (input, source_port) = parse_int::<u16>(input)?;
    let input = expect_str(input, " -> ")?;
    let (input, dest_ip) = parse_ip_or_host(input)?;
    let input = expect_byte(input, b':')?;
    let (input, dest_port) = parse_int::<u16>(input)?;
    Ok(ConnectionFields { source_ip, source_port, dest_ip, dest_port })
}
```

This is **dramatically faster** than regex because:
- No backtracking (each sub-parser succeeds or fails immediately)
- Type conversion happens during parsing (port is already `u16`, not a string)
- Zero allocation (all string fields are `&str` borrows)
- The compiler can inline and optimise the entire chain

#### Layer 3: Fallback Compiled Regex (For Complex Patterns)

For patterns that genuinely need regex (complex alternations, lookahead, etc.):

1. **Pre-compile at build time** using `regex-automata` -> serialised DFA
2. **Load DFA at startup** with zero-copy deserialisation (no runtime compilation)
3. **Use `regex-automata` one-pass DFA** for patterns with capture groups (fastest regex capture)

```rust
// Build time: compile and serialize
let dfa = dense::Builder::new().build(pattern)?;
let bytes = dfa.to_bytes_little_endian();
std::fs::write("dns_query.dfa", bytes)?;

// Runtime: load with zero compilation cost
static DFA_BYTES: &[u8] = include_bytes!("dns_query.dfa");
let dfa = dense::DFA::from_bytes(DFA_BYTES)?.0;
```

#### Layer 4: The Conversion Pipeline

For the elastic_to_rust transpiler, grok processor conversion works like this:

```
Grok pattern string
    |
    v
Expand grok aliases (%{IP} -> regex)
    |
    v
Analyse: can each capture group be replaced with a Layer 1 parser?
    |
    ├── YES (all groups have efficient replacements)
    |       -> Generate Layer 2 composite parser function
    |
    ├── PARTIAL (some groups replaceable)
    |       -> Generate hybrid: efficient parsers for known parts,
    |          regex-automata DFA for complex parts
    |
    └── NO (irreducibly complex regex)
            -> Generate Layer 3 pre-compiled DFA
```

### Underlying Crate Dependencies

| Crate | Purpose | Why |
|---|---|---|
| `memchr` | SIMD byte/substring search | GB/s delimiter scanning, line splitting |
| `simd-json` | JSON parsing | 2-3x faster than serde_json for Kafka messages |
| `nom` or `winnow` | Parser combinators | Zero-copy structured parsing for complex formats |
| `logos` | Lexer generation | Compile-time DFA tokenizer, 800+ MB/s |
| `aho-corasick` | Multi-pattern search | SIMD Teddy algorithm, event routing/classification |
| `regex-automata` | Pre-compiled DFA regex | Zero-cost startup, serialisable DFAs for fallback patterns |
| `chrono` | Timestamp parsing | Date/time handling for `date` processor |
| `serde` + `serde_json` | Serialisation | Event struct (de)serialisation (simd-json is serde-compatible) |

### Performance Expectations

Based on published benchmarks and the nature of the replacements:

| Operation | Regex/Grok | Efficient Rust | Speedup |
|---|---|---|---|
| IP address parse | ~200ns | ~15ns | ~13x |
| Timestamp parse (ISO8601) | ~500ns | ~40ns | ~12x |
| Integer parse | ~100ns | ~10ns | ~10x |
| Syslog header (5 fields) | ~2μs | ~100ns | ~20x |
| JSON parse (1KB event) | ~3μs (serde) | ~1μs (simd-json) | ~3x |
| Full DNS log line (8 fields) | ~5μs | ~300ns | ~15x |

These are order-of-magnitude estimates. Actual gains depend on pattern complexity and data characteristics.

## 3. JSON Parsing from Kafka (Hot Path)

Since all input is JSON from Kafka, the deserialisation layer is critical.

### simd-json

**Crate:** [simd-json](https://github.com/simd-lite/simd-json) | [docs.rs/simd-json](https://docs.rs/simd-json)

- Rust port of simdjson. Uses SIMD (AVX2/SSE4.2/NEON) for structural character detection
- **Throughput:** 450-1380 MB/s depending on document shape (vs 330-560 MB/s serde_json)
- **Serde compatible** - drop-in replacement in many cases
- **`known-key` feature** - switches to fxhash for memoisable key hashing, significant speedup for well-known field names (perfect for ECS fields)
- **Used by Tremor** for production event processing at scale

### Recommended Kafka Consumer Stack

| Component | Crate | Notes |
|---|---|---|
| Kafka consumer | `rdkafka` | librdkafka Rust bindings, production-grade |
| JSON deserialise | `simd-json` | SIMD-accelerated, serde-compatible |
| Event type | Custom `Event` struct | `serde_json::Value` or typed with `#[serde(flatten)]` |

### Zero-Copy Opportunity

Kafka messages arrive as byte slices. With simd-json's `BorrowedValue`, string fields can be borrowed directly from the Kafka message buffer without allocation:

```rust
// Zero-copy parse: string values borrow from msg_bytes
let mut msg_bytes = kafka_message.payload().to_vec(); // one copy from Kafka
let value: simd_json::BorrowedValue = simd_json::to_borrowed_value(&mut msg_bytes)?;
```

## 7. Monorepo Structure (Converter + Runtime In One Repo)

### Why Monorepo

The elastic_to_rust converter should live **inside this repo**, not separately. Reasons:

1. **Tight coupling** - The converter generates Rust code that calls this project's runtime API (Event, Transform trait, dfe-parse functions). Every template change must match the runtime. Separate repos means cross-repo version coordination hell.
2. **Single CI pipeline** - Generate code -> compile it -> run tests against Beats test data, all in one `cargo test`. No multi-repo orchestration needed.
3. **Atomic changes** - When you change the Event API or add a new parser function, you update the codegen templates AND the runtime in one commit. No "update converter, tag, update runtime, hope versions match" dance.
4. **The converter is a build tool, not a product** - It runs at dev time to generate transform modules. It's tooling for this project, not a standalone deliverable.
5. **elastic_to_vrl already bundles everything** - It has the parser, pipeline structs, processors, AND output in one repo. We're following the same proven pattern.

### Test Harness Design

```rust
// tests/integration.rs
use dfe_runtime::Event;
use dfe_transforms::filebeat;

#[test]
fn test_filebeat_dns() {
    run_transform_test(
        "tests/fixtures/filebeat/dns/input.log",
        "tests/fixtures/filebeat/dns/expected.json",
        filebeat::dns::transform,
    );
}

fn run_transform_test(
    input_path: &str,
    expected_path: &str,
    transform_fn: fn(&mut Event) -> Result<()>,
) {
    let inputs = load_test_events(input_path);
    let expected = load_expected_outputs(expected_path);

    for (i, (mut input, expected)) in inputs.zip(expected).enumerate() {
        transform_fn(&mut input).expect(&format!("transform failed on event {i}"));
        assert_json_eq!(
            input.as_value(),
            &expected,
            "Mismatch on event {i}"
        );
    }
}
```

### Validation Approach

1. **Exact match** - Default. Output JSON must match expected JSON field-for-field.
2. **Semantic match** - For fields with non-deterministic values (timestamps with "now", UUIDs), use field-level matchers.
3. **Subset match** - For fields we intentionally don't populate (e.g., `host.name` set by Beats itself, not by the ingest pipeline), ignore missing fields.

Each test file should document which match mode it uses.

## 10. Key Decisions Still Needed

1. **nom vs winnow** - winnow has better DX but nom has larger ecosystem. Recommend winnow for new code.
2. **Event representation** - `serde_json::Value` (simpler) vs custom typed structs (faster but more codegen). Recommend `serde_json::Value` initially, optimise later.
3. **Codegen approach** - proc macros (compile-time) vs build.rs (build-time) vs standalone binary (like elastic_to_vrl). Recommend standalone binary initially (easier to debug), consider proc macros for the parser library.
4. **Enrichment data loading** - embedded vs file-based vs shared memory. MaxMind databases are ~70MB; mmap is appropriate.
5. **Error handling strategy** - drop on error vs route to dead-letter. Recommend configurable per-transform.
